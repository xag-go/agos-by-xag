# Who owns what: AGOS and Hermes

## The rule

AGOS only **shows** and **controls**. Hermes is the engine and holds everything it
has a place for. AGOS keeps **no copy** of anything Hermes holds: it reads Hermes
when it needs something, and it writes through Hermes (its CLI, or its own code run
in its runtime).

AGOS still has data of its own. Each piece is in one of two classes. Nothing else
is allowed:

- **AGOS_ONLY**: product or control data that Hermes has no place for (the owner's
  workspaces, the link from an AGOS chat to its Hermes session,
  backups, Telegram cards…). It has a one-line reason. Where Hermes has something
  close, the reason gives the evidence in Hermes v0.22.2 (`H: <path>`).
- **MOVE_ONCE**: a value from an older AGOS that is read only to move it into
  Hermes (or to drop it). The code that moves it then deletes it. The entry says
  where the value lives in Hermes now.

## Where it is written down

`services/core/src/agos_core/db/ownership/` is the one list (a package: tables by area, keys,
files). It holds every table
and view, every column, and every `app_settings` key or key prefix (`name.*` = a
fixed prefix plus an id), each with its class and reason. Its files part (the files
AGOS keeps outside the database) is in `db/ownership/files.py`, re-exported by
the package.

When you add a table, a column or a setting, you add it to this file with its reason
in the same change. If you can't write an AGOS_ONLY reason, the thing belongs in
Hermes.

## How the code enforces it (on every test run)

`services/core/tests/test_ownership.py` (it reads the code with
`tests/ownership_scan.py`):

1. **Schema.** It builds the schema by running every migration into an in-memory
   database. A table, view or column that is missing from the registry fails. So
   does a registered one that the schema no longer has.
2. **Settings keys.** It reads the code for every `app_settings` key: in
   `get_setting` / `set_setting` calls and in SQL on `app_settings`, whether the key
   is a literal, a constant, `PREFIX + id`, `.format`, an f-string or a small helper.
   It also reads the keys the migrations leave behind. A key missing from the
   registry fails, and so does a registered key that nothing names any more. A key
   the scan can't read also fails; write it as a literal or a module constant.
3. **Reasons.** An empty reason fails. A MOVE_ONCE entry without its Hermes place
   fails, and so does a MOVE_ONCE key that nothing deletes (code or migration).
4. **Evidence.** Every `H: <path>` must exist in the Hermes checkout
   (`~/.hermes/hermes-agent`, or `AGOS_HERMES_SOURCE`). The test is skipped when
   there is no checkout. So a Hermes update that moves a file shows up here.
5. **Work in flight.** An entry can carry `moving=(branch, N)`, meaning another
   branch is changing it. The mark is valid only while there are exactly N
   migrations. So a merge that adds migrations fails until someone checks the entry
   against the merged code and removes the mark.

`services/core/tests/test_hermes_writes_guard.py` covers Hermes's own files:
`.env`, `profile.yaml`, `gateway.parked`, `cron/jobs.json`, `config.yaml`,
`state.db`, `kanban.db`, `SOUL.md`, `MEMORY.md`, `USER.md` and
`webhook_subscriptions.json` and `channel_aliases.json`. Any AGOS module that writes one of these files fails,
unless `ALLOWED` lists that module with a reason. The guard catches these writes:

- `write_text`, a move over the file, removal, and `open` for writing;
- a writable `sqlite3.connect` (opening the file read-only is allowed);
- a write through a name bound to the path, a constant (including a dict of file
  names), a function that returns the path, or a helper that writes the path it is
  given.
